# 夜間行為：提示收工，不停止計時

**日期**：2026-08-08
**狀態**：已實作

## 原始想法

> 希望晚上（紫外線 < 1）時鐘自動停止計時，以及晚上的時候不開啟計時器。

方向是對的——夜間確實不需要補擦提醒。但「停止計時」與「用 UV 值判定」這兩個做法都不能照做。

## 為什麼不能把 UV 接進倒數

### 一、會打破事件溯源的決定性

`reduceSession` 的輸入只有 `{ stream, revision, clock }`。整個 `packages/domain/src` 沒有任何 `uvi`／`forecast`／`weather` 參照——投影是「事件流 ＋ 時鐘」的純函式。

天氣一旦參與計算，同一組事件重播會依當下快取到什麼而給出不同結果。**S-10 更正整條機制就建立在「重播事件流會得到同樣答案」之上**：replace 一筆事件後 reducer 重跑，稽核鏈才成立。這個保證不能為了夜間行為而破壞。

### 二、現有資料回答不了「現在 UV < 1」

`DaytimeUvForecast` 是**每日日間** UVI（五天，每天一個值），沒有逐小時資料。而且它需要先設定地區才有、是快取、可能過期，`/v1/uv/forecast` 的後端目前也還沒實作。

把核心倒數綁上它，等於讓沒設地區的人（多數初次使用者）連倒數都不能用——核心迴圈不該依賴一個經常缺席的網路資源。

### 三、暫停之後恢復是假安全感

這點最危險。18:00 擦防曬、19:00 凍結時還剩 40 分鐘、隔天 06:00 恢復——畫面會顯示「還有 40 分鐘」，但那層防曬已經是 12 小時前的了。

**暫停只有在「永不恢復」的前提下才安全。** 這正是 AC-66 與整個產品在防的假安全感。

## 決策

**夜間不是「暫停倒數」，是「這次防護結束了」。**

| 項目 | 做法 |
| --- | --- |
| 判定 | `isFixedEvening()`（`apps/web/src/features/uv/uvForecastRules.ts`）——固定本地時段 18:00–06:00，離線可用、不需地區、不需後端 |
| 提醒頁 | 夜間且有進行中 Session 時顯示收工提示，提供「結束本次提醒」與「保持進行中」。結束走既有的 `sessionControl.endCurrentSession`，不新增結束路徑 |
| 設定步驟 2 | 夜間顯示說明，**不阻擋建立**。夜間登山、清晨四點出發、人工 UV 都是合法情境；設定流程剛拿掉一道硬關卡，不該再加一道 |
| 騷擾控制 | 比照 `getEveningCycleKey()` 的每晚一次機制，關掉後同一夜間週期不再出現（跨午夜算同一晚） |
| 倒數本身 | **完全不動。** 時鐘照走 |

`NightWindDownPrompt.test.ts` 有一則測試斷言文案含「倒數會繼續進行」、且不含「已暫停」「停止計時」——避免之後有人把這個元件改成真的凍結時鐘。

## 之後真的要讓 domain 知道情境，走這條

「進入室內／返回戶外」是 `context_changed`，S-09 規格第一層十項事件裡尚未實作的四項之一。那是**使用者主動回報的事件**，透過既有的事件流進 reducer，不破壞決定性。

需要「App 知道現在不用曬」時，實作那個事件，**不要再考慮把天氣接進 reducer**。
