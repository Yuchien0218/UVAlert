## 二、`/setup` 右上角叉叉改「回上一頁」

**狀態：✅ 已裁決並實作（2026-08-30）——改「回上一頁」，草稿保留**

實作 commit `b945902`。按鈕同時從右上移到左上（返回是導航，導航在左上是慣例），圖示 `tool-close` → `tool-arrow-left`，emit `cancel` → `back`。新增守門測試「返回鈕發出 back 而不是 cancel」，已驗證會紅。`controller.cancel()` 自此沒有 UI 呼叫者，未移除但已加註解。**尚未做視覺實測**——`/setup` 有 `requiresNoActiveSession` 守衛，這台裝置有活動的測試 session，進不去；不擅自結束他人的 session 資料。

**現況（已讀碼確認，不是推測）**：

- 按鈕的 `aria-label` 是「取消設定」（`SetupStepShell.vue:56`），**語意與行為是一致的**
- `cancel()` → `setup.cancel()` → `deleteDraft(draftId)`，**真的把草稿刪掉**，然後 `router.replace({ name: "home" })`（`SetupPage.vue:211`、`createSetupController.ts:482`）
- 版面問題實測（390×844）：`main` 頂端 y=72、叉叉 y=96（44×44）、`<h1>` 頂端 y=95。叉叉與標題幾乎同高，卻各佔一列，把標題往下推

### 建議：改「回上一頁」，草稿保留

1. **「回上一頁」在任何 App 裡都是純導航，使用者不會預期它刪東西。** 若改了文案卻仍刪草稿，就是用一個看起來安全的按鈕做破壞性動作——那比現在的叉叉更糟，現在的叉叉至少還誠實地標著「取消設定」。

2. **續作路徑已經蓋好了，不需要新機制。** `SetupPage.vue:294` 已經有完整的「繼續未完成的設定？／繼續設定／重新開始」回復卡，`resumeDraft()` 與 `restartDraft()` 都在，`SetupDraftV1.currentStep` 也還在契約裡。保留草稿只是讓這套既有機制真正被用到——現在它被叉叉的刪除行為繞過了。

3. **取消草稿的能力不會消失**，它移到回復卡的「重新開始」上，那裡的語意是明確的。

**實作時必須驗證的前提**：離開再回到 `/setup` 時，`recoveryPendingState` 要真的觸發回復卡。若沒觸發，使用者會看到一個「半填好但沒說明為什麼」的表單，那比刪掉更糟。這一條要當成守門測試寫。

## 三、首頁「各部位狀態」8 個 pill

**狀態：✅ 已裁決並實作（2026-08-30）——兩個都做**

實作 commit 見下方。**實測把根因看得更清楚了**：8 個部位全是 `tracking`（倒數正常跑），`reasonCodes` 都只有 `PRODUCT_IDENTITY_UNKNOWN`——所以畫面上是同一句話重複八次，而「N 個原因」這個數字不告訴使用者任何事（不知道是什麼原因、也不知道要不要處理）。

先修根因，再加收合。

- **根因**：那個「・1 個原因」是 `PRODUCT_IDENTITY_UNKNOWN`（標示尚未確認）。對不填防曬乳的使用者，它會**永遠**顯示在每一個部位上。單純收合只是把它遮住，雜亂的來源還在。
- **順序**：先讓這個原因不逐部位重複，再把 pill 收成狀態摘要、需要時展開。

### 實作結果

1. **移除 pill 的「・N 個原因」**，改成群組層級的共有說明——只有**每一個**部位都帶該原因時才顯示，少一個就不顯示（寧可不說，也不要說得比實際情況廣）。
2. **只做 `PRODUCT_IDENTITY_UNKNOWN` 一個碼**，不做 21 個 ReasonCode 的全表：其餘的碼要嘛是事件型（流汗、毛巾、碰水），效果已經反映在 `timingStatus`／群組標題上；要嘛會讓部位落到別的群組。自創 21 條健康相關文案的風險也不划算。
3. **收合只給 `tracking` 與 `not_applicable`**（「現在不用做事」的狀態），且部位數 > 1 才做。需要行動的狀態常駐——把「建議現在補擦」藏進 disclosure 正是 `DESIGN.md` 第五節展開收合契約要避免的事。
4. 觸發器用契約允許的「標籤化按鈕」，`aria-expanded` ＋ `aria-controls` 齊備，chevron 換圖示 name 不用 `transform: rotate`。

**已知未做**：`reminderPresentation.ts` 裡 `PRODUCT_IDENTITY_UNKNOWN` 的文案仍寫「暫時無法建立補擦倒數」「未計時」，與 2026-08-30 的保守倒數規則矛盾。目前**不會顯示**（那段只在真的沒有倒數時走到），所以不是活躍 bug，但是個陷阱。

## 六、首頁主 CTA 的份量：「記錄狀況」不該是主要 CTA

**狀態：使用者 2026-08-30 提出，方向待裁決。**

**先講結論：這件事先前沒有被記錄，而且現有文件寫的是相反的。** 使用者問「之前有記錄到嗎」——查了 `docs/` 全部非 archive 文件，沒有任何一條說首頁不該有主 CTA，能找到的都要求它存在：

| 出處                                                                                | 寫的是什麼                                 |
| ----------------------------------------------------------------------------------- | ------------------------------------------ |
| `2026-08-15-redesign-sitemap-userflow-current.md` 第 199 行（**現行 UX／IA 基準**） | 「首屏維持不捲動就看得完倒數與**主 CTA**」 |
| `docs/design/2026-08-17-home-wireframe-variants-design.md` 第 29 行                 | 「單一主要 CTA『記錄補擦』」               |
| `DESIGN.md` 第 736、834 行                                                          | 「每頁只有一個主要 CTA」                   |

所以這是**推翻既有裁決**，不是補一個漏掉的待辦。

### 一個對裁決有影響的區分

首頁那顆按鈕的文字不是固定的，它跟著 `primaryAction.actionKind` 走（`reminderPresentation.ts` 的 `ACTION_LABELS`，共 13 種）。實務上最常見的兩種是：

| 狀態                                       | 按鈕文字     | 這時它該不該是主 CTA                                                                             |
| ------------------------------------------ | ------------ | ------------------------------------------------------------------------------------------------ |
| `tracking`（倒數進行中，例如還有 82 分鐘） | 「記錄狀況」 | **這正是使用者質疑的**——還有 82 分鐘，沒有要使用者現在做任何事，卻用深杏桃實心大按鈕佔滿整個寬度 |
| `reapply_due`（該補擦了）                  | 「記錄補擦」 | 這時它**就是**當下最主要的任務，降級反而不對                                                     |

**所以「要不要當主 CTA」很可能不該一刀切，而是跟著狀態走。** 這與 `2026-08-23-wireframe-copy-fixes.md` 第 208 行對裝備詳情頁下的裁決是同一個模式（「主 CTA 依狀態切換，不是固定文字」）。

### 好消息：不違反設計系統

`DESIGN.md` 的「每頁只有一個主要 CTA」是**上限不是下限**——`2026-08-23-wireframe-copy-fixes.md` 第 145 行已經明文解釋過，並據此讓夜間頁完全沒有主 CTA。所以首頁在某些狀態下不放主 CTA，**不需要改設計系統**。

### 動手前要裁決的

1. **是所有狀態都降級，還是只有 `tracking`？** 建議只降 `tracking`（與 `not_applicable` 之類「現在不用做事」的狀態），`reapply_due`／`reapply_soon` 維持主 CTA。
2. **降級成什麼？** `.button--quiet`（既有的次要樣式）？還是文字連結？還是移到「最近事件」附近而不是倒數正下方？
3. **`2026-08-15` 現行 sitemap 第 199 行要跟著改**——它現在寫「首屏維持不捲動就看得完倒數與主 CTA」。

### 使用者補充的方向（2026-08-30）

> 「因為此 APP 核心功能是提醒補擦，事件現在是深色按鈕，會一直注意到這個事件的存在。我希望降級，或者變成是『有大量流汗的狀況嗎？提醒您記得補擦防曬』類似的次要提醒。」

這個方向本質是**把命令式的主 CTA 換成條件式的提問**，而且它跟 domain 的語意是相符的——情境事件（流汗／毛巾／摩擦／洗手／下水）**本來就是條件觸發**的，不是每次都要做。深杏桃實心滿寬按鈕讀起來是「你現在該做這件事」，與「如果剛好有發生，才需要點」不是同一件事。

### 文案規範上的兩個硬性限制（查證後）

1. **不能用「您」。** `2026-08-23-wireframe-copy-fixes.md` §2.3 有實測紀錄：`apps/web/src/` 之中「您」出現 **0 次**、「你」出現 **41 次**，全站一致用「你」。所以「提醒**您**記得補擦防曬」要改成「你」，或乾脆不用第二人稱。
2. **「記錄補擦」是 copy-audit 訂的核心動作詞彙**（`2026-08-17-copy-audit.md`「本次統一規則」），`reapply_due` 狀態下的文字不該自行改寫。

### 建議方案

**依狀態切換份量，不要一刀切**——與 `2026-08-23-wireframe-copy-fixes.md` 第 208 行對裝備詳情頁的裁決同一個模式。

| 狀態                       | 現況                           | 建議                                                     |
| -------------------------- | ------------------------------ | -------------------------------------------------------- |
| `tracking`／`reapply_soon` | `.button--primary`「記錄狀況」 | **降級**：改次要樣式，文案改條件式提問                   |
| `reapply_due`              | `.button--primary`「記錄補擦」 | **維持主 CTA**——這時它就是當下最主要的任務，降級反而不對 |

文案方向（避開「您」、涵蓋五種狀況而不只流汗）：

- 「流汗、碰水或擦過了嗎？」＋次要按鈕「記錄狀況」
- 或「剛才有流汗、碰水或擦拭嗎？記錄後會重算補擦時間。」
