## 二、`/setup` 右上角叉叉改「回上一頁」

**狀態：✅ 已裁決並實作（2026-08-30）——改「回上一頁」，草稿保留**

實作 commit `b945902`。按鈕同時從右上移到左上（返回是導航，導航在左上是慣例），圖示 `tool-close` → `tool-arrow-left`，emit `cancel` → `back`。新增守門測試「返回鈕發出 back 而不是 cancel」，已驗證會紅。`controller.cancel()` 自此沒有 UI 呼叫者，未移除但已加註解。**尚未做視覺實測**——`/setup` 有 `requiresNoActiveSession` 守衛，這台裝置有活動的測試 session，進不去；不擅自結束他人的 session 資料。

**現況（已讀碼確認，不是推測）**：

- 按鈕的 `aria-label` 是「取消設定」（`SetupStepShell.vue:56`），**語意與行為是一致的**
- `cancel()` → `setup.cancel()` → `deleteDraft(draftId)`，**真的把草稿刪掉**，然後 `router.replace({ name: "home" })`（`SetupPage.vue:211`、`createSetupController.ts:482`）
- 版面問題實測（390×844）：`main` 頂端 y=72、叉叉 y=96（44×44）、`<h1>` 頂端 y=95。叉叉與標題幾乎同高，卻各佔一列，把標題往下推

### 建議：改「回上一頁」，草稿保留

1. **「回上一頁」在任何 App 裡都是純導航，使用者不會預期它刪東西。** 若改了文案卻仍刪草稿，就是用一個看起來安全的按鈕做破壞性動作——那比現在的叉叉更糟，現在的叉叉至少還誠實地標著「取消設定」。

2. **續作路徑已經蓋好了，不需要新機制。** `SetupPage.vue:294` 已經有完整的「繼續未完成的設定？／繼續設定／重新開始」回復卡，`resumeDraft()` 與 `restartDraft()` 都在，`SetupDraftV1.currentStep` 也還在契約裡。保留草稿只是讓這套既有機制真正被用到——現在它被叉叉的刪除行為繞過了。

3. **取消草稿的能力不會消失**，它移到回復卡的「重新開始」上，那裡的語意是明確的。

**實作時必須驗證的前提**：離開再回到 `/setup` 時，`recoveryPendingState` 要真的觸發回復卡。若沒觸發，使用者會看到一個「半填好但沒說明為什麼」的表單，那比刪掉更糟。這一條要當成守門測試寫。

## 三、首頁「各部位狀態」8 個 pill

**狀態：✅ 已裁決並實作（2026-08-30）——兩個都做**

實作 commit 見下方。**實測把根因看得更清楚了**：8 個部位全是 `tracking`（倒數正常跑），`reasonCodes` 都只有 `PRODUCT_IDENTITY_UNKNOWN`——所以畫面上是同一句話重複八次，而「N 個原因」這個數字不告訴使用者任何事（不知道是什麼原因、也不知道要不要處理）。

先修根因，再加收合。

- **根因**：那個「・1 個原因」是 `PRODUCT_IDENTITY_UNKNOWN`（標示尚未確認）。對不填防曬乳的使用者，它會**永遠**顯示在每一個部位上。單純收合只是把它遮住，雜亂的來源還在。
- **順序**：先讓這個原因不逐部位重複，再把 pill 收成狀態摘要、需要時展開。

### 實作結果

1. **移除 pill 的「・N 個原因」**，改成群組層級的共有說明——只有**每一個**部位都帶該原因時才顯示，少一個就不顯示（寧可不說，也不要說得比實際情況廣）。
2. **只做 `PRODUCT_IDENTITY_UNKNOWN` 一個碼**，不做 21 個 ReasonCode 的全表：其餘的碼要嘛是事件型（流汗、毛巾、碰水），效果已經反映在 `timingStatus`／群組標題上；要嘛會讓部位落到別的群組。自創 21 條健康相關文案的風險也不划算。
3. **收合只給 `tracking` 與 `not_applicable`**（「現在不用做事」的狀態），且部位數 > 1 才做。需要行動的狀態常駐——把「建議現在補擦」藏進 disclosure 正是 `DESIGN.md` 第五節展開收合契約要避免的事。
4. 觸發器用契約允許的「標籤化按鈕」，`aria-expanded` ＋ `aria-controls` 齊備，chevron 換圖示 name 不用 `transform: rotate`。

**已知未做**：`reminderPresentation.ts` 裡 `PRODUCT_IDENTITY_UNKNOWN` 的文案仍寫「暫時無法建立補擦倒數」「未計時」，與 2026-08-30 的保守倒數規則矛盾。目前**不會顯示**（那段只在真的沒有倒數時走到），所以不是活躍 bug，但是個陷阱。

### 重新匯出時要交出哪些檔案（2026-08-31 查證）

**兩種格式都要，不是二選一。**

| 檔案 | 格式 | 尺寸 | 誰在用 |
| ---- | ---- | ---- | ------ |
| `favicon.svg` | **SVG** | viewBox 64×64 | 現代瀏覽器的分頁圖示（`index.html` 的 `rel="icon" type="image/svg+xml"`）。**已於 2026-08-31 更新**，重畫時沿用同一個 viewBox |
| `favicon.ico` | **ICO** | 內含 32×32 | 舊瀏覽器的後備（`rel="icon" sizes="32x32"`）。不能用 PNG 副檔名替代，那條 link 指名 `.ico` |
| `apple-touch-icon.png` | **PNG** | 180×180 | iOS 主畫面。**iOS 不讀 manifest 也不吃 SVG**，只認這一個檔 |
| `icon-192.png` | **PNG** | 192×192 | manifest，`purpose: any` |
| `icon-512.png` | **PNG** | 512×512 | manifest，`purpose: any` |
| `icon-512-maskable.png` | **PNG** | 512×512 | manifest，`purpose: maskable` |

manifest 明寫 `"type": "image/png"`，所以那四個**必須是 PNG**，換成 SVG 會被忽略。

#### ⚠️ 目前 `icon-512.png` 與 `icon-512-maskable.png` 是同一個檔

2026-08-31 實測兩者的 MD5 完全相同（`d91b8c26…`）。**maskable 沒有自己的安全邊界。**

maskable 的用途是讓 Android 依各家 launcher 的形狀（圓形、圓角方形、水滴）自行裁切，所以規範要求**重要內容全部落在畫布正中央、直徑 80% 的圓內**——等於四邊各留至少 10% 的餘裕。兩個檔案一樣就表示 `any` 那版的構圖被直接當成 maskable 用，在圓形 launcher 上邊緣會被切掉。

所以重新匯出時，**512 要出兩個不同的檔**：

- `icon-512.png`：構圖可以貼滿一點（`any` 不會被裁）
- `icon-512-maskable.png`：同一個標記再縮小一級，確保落在中央 80% 圓內

要完成 PNG 的部分，需要**其中一條**：

1. 由使用者用設計工具依 `favicon.svg` 的新幾何重新匯出（transform 的數字已寫在該檔的註解裡，可直接照抄）
2. 或在 repo 加一個 rasteriser 與對應的 `pnpm` 指令，把 public 的圖示納入產生器管理

**第 2 條其實是這次問題的根因**：2026-08-30 更新 logo 時，橫式 lockup 改了但 app icon／favicon 沒跟上，正是因為兩者之間沒有任何自動化連結。

**maskable 那一張要單獨檢查**：Android 會把它裁成圓角方形，放大標記會壓縮安全邊界。5.3 的放大**不應該無差別套到 maskable**。

## 十三、今日 UV 顯示台灣分布地圖（2026-08-31 使用者提出）

### 13.1 幾何不用外找，repo 裡已經有官方版本

`apps/web/src/generated/region-boundaries.generated.json` 是**內政部國土測繪中心「鄉鎮市區界線(TWD97 經緯度)」**（dataset 7441，2025-03-18 版，政府資料開放授權條款第 1 版），368 個鄉鎮的 GeoJSON MultiPolygon，含 bbox。由 `pnpm region-data:build` 從官方 SHP 產生、`pnpm region-data:verify` 驗證可重現。

目前只有一個用途：`LazyTaiwanRegionResolver` 拿它做 point-in-polygon 反查地區。

**所以不建議引入 taiwan.md 的形狀檔**——那會多一份來源、多一份授權要確認，而且跟現有的 `regionCode` 對不上。用自己的來源，畫出來的縣市邊界跟地區選單、反查邏輯天生一致。

**但有兩個必須解的問題**：

| 問題 | 說明 |
| --- | --- |
| **13.5MB** | 直接進 bundle 不可行。目前是 `await import()` 動態載入，只在需要反查時才付代價 |
| **粒度是鄉鎮不是縣市** | 要畫縣市圖得先合併 368 → 22（`countyCode` 已經在 properties 裡，可以 dissolve） |

建議做法：在 `tools/region-data/` 加一個**縣市層級 ＋ 大幅簡化**的產出（Douglas–Peucker 之類），目標 < 100KB 的 SVG path 或精簡 GeoJSON。這是既有產生器的延伸，不是新機制；`region-data:verify` 的可重現性檢查也一起涵蓋。

### 13.2 UV 資料不用新增上游呼叫

`supabase/functions/_shared/cwa.ts` 的 `fetchCwaDataset()` **抓的是整份 F-D0047-091 資料集**（沒有地點參數，靠 ETag 快取），然後 `mapCwaForecast()` 才用 `Geocode` 濾出使用者那一個縣市（`regionCode.slice(0, 5) + "000"`）。

**也就是說 22 個縣市的 UV 值早就在同一份回應裡了**，只是被丟掉。做全臺地圖不需要打 22 次 API、不需要換資料集、不會增加 CWA 的用量——只要多一個回傳形狀（例如 `/v1/uv-forecast?scope=nationwide`）把所有 `Geocode` 都映射出來。

顏色也不用新訂：`DESIGN.md` 第二節已有 **UV 五級風險色**，`--color-uv-*` 系列已存在且已套用在五日預報的等級標籤上。地圖填色直接用同一組，全站語意一致。

### 13.3 三個要裁決的地方

1. **放哪裡？** 使用者說「今日 UV」。目前 `/forecast` 是五日預報，首頁只有一個 UV 數字。地圖是放進 `/forecast` 當第二個區塊，還是首頁？（首頁有「不捲動就要看完倒數、狀態與下一步」的實測約束，塞地圖要很小心。）
2. **可以點嗎？** 點縣市直接切換地區，會讓它同時是「資訊圖」與「地區選擇器」——那其實是 §12.4「`/region` 太長」的一個潛在解法，但也讓範圍變大。
3. **無障礙怎麼處理？** 色塊地圖對色覺障礙者與螢幕閱讀器都不夠。至少要有一份等價的文字／表格呈現（`DESIGN.md` 的可及性要求），不能只有圖。

### 13.4 建議的最小第一版

先做**不可點的靜態縣市圖**放在 `/forecast` 現有五日卡下方：只填色、標自己所在的縣市、附一句「這是地區預報，不是即時測站觀測」。旁邊保留現有的縣市 UV 列表當文字等價物。

理由：它不動任何既有流程，不需要新的互動狀態，而且**能先驗證最貴的那一步**（把 13.5MB 的鄉鎮界線壓成 <100KB 的縣市輪廓）到底做不做得出來。若那一步不成立，後面的互動設計都不用談。
