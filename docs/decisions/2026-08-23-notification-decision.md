**日期**：2026-08-23（Asia/Taipei）
**狀態**：現行裁決——已決定實作，尚未動工。
**裁決**：**做 service worker ＋ 本機通知。**
**影響範圍**：產品核心價值、wireframe 可畫的狀態、`/help/how-it-works` 內容能否發布。

> **2026-08-31 歷史註記與現行裁決**：下方 `canDeliverInBackground=false` 與「不含後端 Web Push」是 2026-08-23 的歷史事實，必須保留，不能倒寫為當時已有後端能力。後續 remote Web Push 已完成 local scope 的實作；Task 9 只提供本機可部署證據，production enablement 仍需 Task 10 的 current evidence，裝置 smoke 仍需 Task 11 的 dated evidence。現行裁決是：本機通知保留為 fallback；只有在支援、設定與裝置條件都成立時，remote Web Push 才提供背景提醒。它仍不保證瀏覽器完全關閉、系統休眠或平台限制下的送達；iPhone/iPad 必須把網站加入主畫面、從主畫面 Web App 開啟並允許通知，詳見目前[通知設定文案](../../apps/web/src/pages/settings/NotificationSettingsPage.vue)。

## 摘要

盤點時發現：**這個 App 目前沒有任何通知能力，一行相關程式碼都沒有。**

倒數只在分頁開著時存在。關掉分頁，沒有任何東西會提醒使用者補擦——而「提醒補擦」正是這個產品的核心承諾。

規格、設計與圖示三層**都假設通知存在**，只有程式碼沒有。這不是「通知失效的處理」問題，是「通知從未實作」。

`apps/web/src/pages/InstallPage.vue:102` 是唯一誠實的一句：

> 安裝不會讓系統在關閉頁面後保證送出通知。

但這句仍低估現況——正確說法是「目前沒有通知」。

### 連帶結論：目前不是功能意義上的 PWA

有 `manifest.webmanifest` 與圖示，所以可以加到主畫面；但**沒有 service worker**，因此沒有離線 App Shell，也沒有任何背景能力。

## 三、裁決

考慮過的三條路：

| 選項          | 內容                                                                                          | 結果                                                             |
| ------------- | --------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| **A（採用）** | 做 service worker ＋ 本機通知                                                                 | **採用**。不需要後端；`showNotification` ＋ 排程可涵蓋主要情境   |
| B             | 明確承認不做，改定位為「開著查看用的補擦計算器」，撤掉所有通知文案、banner 狀態與已畫好的圖示 | 不採用                                                           |
| C             | 維持現狀（規格說有、程式沒有）                                                                | **明確否決**。wireframe 會照規格畫出通知狀態，畫完才發現無處可接 |

選 A 的理由：一個「防曬補擦提醒 App」若不會提醒，核心價值不成立。本機通知不需要後端即可交付，成本遠低於它挽回的產品價值。

### 範圍界定

- **本機通知**（service worker ＋ `showNotification` ＋ 排程），不含後端 Web Push。
- 涵蓋情境：使用者關掉分頁但瀏覽器仍在、或已安裝到主畫面。
- 不承諾：瀏覽器完全關閉、系統強制休眠、iOS PWA 的已知平台限制。

## 四、對其他工作的影響

### 4.1 解除 wireframe 的阻塞

通知狀態現在有明確落點，wireframe 可以放心畫：`DESIGN.md` 已定義的 banner 狀態與已完成的四個圖示都能對接。

### 4.2 `/help/how-it-works` 內容不得照原文發布

PRD §13.5 Q2／Q3 的原文大量描述通知行為，例如：

> P0 在網頁前景顯示提醒……若 P1 啟用 Web Push，後端會保存提醒排程
>
> 通知是輔助功能，可能受通知權限、網路、系統省電、專注模式、清除資料或解除安裝影響

在通知實作完成前發布這段，等於告訴使用者「通知可能因省電模式延遲」——但實際上不會有通知。使用者會誤以為只要調整系統設定就能收到提醒。

**處置**：改寫成誠實版本，說明倒數如何計算、為何關閉分頁重開仍準確（保存絕對時間戳），以及**現階段需要自己回來查看**。改寫後這則正好成為 `mvp-flow-review.md` §1.3 建議（「把後果講清楚」）的落地處。

實作完成後再依實際能力更新。

### 4.3 「更多」頁的通知設定入口

wireframe `selection07` 的「通知設定 → 通知未開啟」在實作完成前不成立，該入口不應先上線。
