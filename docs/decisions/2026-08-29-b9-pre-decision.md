# B9 動工前的裁決點（2026-08-29）

**狀態**：待裁決——本文件是盤點與建議，**不是已確認的決策**。
**用途**：`docs/superpowers/specs/2026-08-27-b9-icon-first-progressive-disclosure-design.md` 有規格但沒有實作計畫，而規格本身跟現行圖示系統有三處衝突。動工前需要先裁決。
**範圍**：只裁決方向與約束，不改任何元件。
**權威性**：低於 `DESIGN.md` 與圖示系統 README。本文件指出它們與 B9 規格的衝突，但在裁決前，**現行規則仍然有效**。

## 一、現況證據

### 圖示確實偏小

全站 46 處 `<Icon>`：**24px 共 29 處、20px 共 21 處、16px 僅 1 處**。最大只到 24px，而 24px 同時扮演三種角色——下排導覽、按鈕內圖示、卡片主視覺。

「更多」頁的入口卡實測（390px 行動版）：

| 項目 | 數值 |
| --- | --- |
| 卡片尺寸 | 304 × 82 |
| 圖示尺寸 | 20 × 20 |
| **圖示佔卡片面積** | **1.61%** |

圖示垂直置中在兩行文字旁邊，四周都是空白——它讀起來是項目符號，不是視覺錨點。雙色圖示的琥珀金重點（書脊、資料庫中間帶、托盤）在 20px 下幾乎看不見。

### 說明文字確實多

- 說明類 class（`__helper`／`__note`／`__body`／`__reason`／`__description`／`__summary`／`caution`）共 **55 處**。
- 段落數最多的五頁：`NotificationSettingsPage`（15）、`ReportContextEventPage`（14）、`EventCorrectionPage`（12）、`DataSettingsPage`（11）、`SetupPage`（10）。

### 但「展開收合」不是新東西——已經有 5 個，而且四種做法

| 元件 | 觸發器 | `aria-controls` | chevron 方向 |
| --- | --- | --- | --- |
| `ProductSnapshotEditor` | `.button--quiet` 按鈕 | ❌ 無 | 換圖示 name（right／down） |
| `RecentEventsList` | `.button--quiet` 按鈕 | ❌ 無 | 沒有圖示，純文字 |
| `ContextSelector` | 整列可點 | ✅ 有 | CSS `rotate(180deg)` |
| `QuickProtectionSummary` | 整個 header 可點 | ❌ 無 | CSS `rotate(180deg)` |
| `NotificationSettingsPage` | 「如何開啟」按鈕 | 待確認 | — |

B9 §4 自己要求「同一種元件只能採一種一致模式」與「設定 `aria-expanded` **與 `aria-controls`**」。**現有實作有 3 個沒有 `aria-controls`，已經違反 B9 自己的契約。**

## 二、裁決點 1：圖示尺寸級距要不要擴充

**衝突**：B9 §2 定義 `--icon-size-inline: 18px`／`--icon-size-action: 24px`／`--icon-size-feature: 32px`。但——

- `DESIGN.md` §8 與圖示系統 README §9 明訂「從 16 / 20 / 24 三個檔位選，**不發明新數值**」。
- `apps/web/src/components/icons/Icon.vue` 的型別就是 `size?: 16 | 20 | 24`，**TypeScript 會直接拒絕 18 與 32**。
- 那三個 `--icon-size-*` token 在 `styles.css` 裡目前一個都不存在。

| 選項 | 內容 | 評估 |
| --- | --- | --- |
| **A（建議）** | **只加 32，拒絕 18**，級距變成 16／20／24／32 | 32 是真的缺的角色；18 不是 |
| B | 完全照 B9 加 18 與 32 | 小尺寸區會變成 16／18／20／24 四檔，而 18 沒有新角色 |
| C | 不擴充，改用留白與底色色塊讓 24px 看起來更有份量 | 成本最低，但解決不了「圖示只佔 1.61%」 |

**建議 A 的理由**：B9 說 18px 是「文字旁的輔助 icon，不主導區塊」——那正是現有 20px 已經在做的事，加 18 只是在 16 與 20 之間多塞一格。而 32px 對應的「卡片或功能入口的主要視覺」現在**沒有任何檔位**，只能拿 24 硬撐，這才是真正的缺口。

採用 A 需要一併回寫：`DESIGN.md` §8 尺寸那行、圖示系統 README §9、`Icon.vue` 的型別、B9 規格 §2 的表格。

## 三、裁決點 2：既有的 5 個展開元件要不要先統一

**建議：先統一，再擴散。**

理由是上面那張表——四個實作三種差異。B9 如果直接開始把更多說明改成可展開，等於把不一致乘以三倍，之後要統一的成本更高。而且其中「沒有 `aria-controls`」是無障礙缺陷，不是風格差異：螢幕閱讀器無法把觸發器與被控制的區塊關聯起來。

統一時要定的是三件事：**觸發器是按鈕還是整列可點**、**chevron 用換 name 還是 CSS 旋轉**、**`aria-controls` 一律要有**。

（chevron 那項有個既有取捨：CSS `rotate(180deg)` 是位移動畫，而 `DESIGN.md` §12 規則一說「只用 opacity，唯一例外是內容進場」。chevron 翻轉屬於「回應手指的直接操作」，統一時要順便決定它算不算第二個例外，還是改用換 name 的做法。）

## 四、裁決點 3：哪些文字絕對不能收

B9 §3 已經列了原則。要疊上去的是**專案既有的兩條規則**：

- `DESIGN.md` §5：**「來源與審閱狀態不能藏在互動之後」**——這是健康內容可查證性的基礎。
- `DESIGN.md` §1 語調：「先給結論再補條件」。收掉「條件」會讓結論失去限制。

用「更多」頁四張卡的說明文字實際分類，示範這件事**不能批次做**：

| 卡片 | 說明文字 | 分類 |
| --- | --- | --- |
| 通知設定 | 「開啟或管理補擦提醒通知。」 | **直接刪**——純重述標題，沒有新資訊 |
| 防曬衛教 | 「用白話讀懂 UV、防曬乳、補擦與曬後照護。」 | **縮短保留**——它告訴你裡面有哪些主題 |
| 安裝到手機桌面 | 「安裝後資料較不易遺失；不安裝也可正常使用。」 | **必須常駐**——這是決策條件（B9 §3「使用者採取動作前必須知道的條件」），而且第二句在防止使用者誤以為非裝不可 |
| 本機資料管理 | 「查看、匯出與清除這台裝置上的資料。」 | **可收**——進去就看得到 |

同一頁四張卡，四種處置。B9 §5 自己也寫「不進行全站批次刪文，也不只靠字數決定是否收合」。

## 五、建議的第一輪範圍

**「更多」頁當試點。** 理由：它是純導覽頁，沒有健康內容、沒有錯誤狀態、沒有不可逆操作，改壞了風險最低；而且它正好是「圖示只佔 1.61%」最嚴重的地方。

做完之後比較展開前後的**理解程度、操作步數與版面高度**（B9 §5 的要求），再決定要不要往設定頁推。

核心提醒流程（`/`、`/setup`、`/reminder/reapply`）**第一輪不要碰**——那是產品的核心迴圈，而且 `DESIGN.md` §6 已經規定提醒頁「先結論、後細節」。

## 六、B9 規格需要回寫的地方

不論上面怎麼裁決，這兩處都已經過期：

1. **§2「icon 放大不能破壞既有 Lucide 線寬」**——`@lucide/vue` 已於 2026-08-29 完全移除，這句話沒有對象了。自訂圖示的線寬固定 2.5、隨 viewBox 等比縮放，放大到 32px 不會有線寬問題。
2. **§2 的尺寸表**——依裁決點 1 的結果修正。

另外 B9 沒有實作計畫檔，`docs/superpowers/plans/README.md` 也沒有它的列。裁決之後要補一份計畫，才有 Task 與驗證清單可循。
