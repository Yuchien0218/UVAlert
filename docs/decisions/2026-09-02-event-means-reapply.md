# 事件＝需要補擦：拆掉「記錄狀況」這個入口

**日期**：2026-09-02
**裁決者**：使用者
**狀態**：已定方向；CTA 與「暫停不做」已落地，流程合併未開始

## 使用者的原則

> 這款 App 的主要功能就是提醒要補擦防曬乳。如果遇到了事件＝需要補擦。

目前的實作不是這樣組織的：「記錄狀況」與「記錄補擦」是兩個平行的目的地，使用者得自己把它們接起來。這份文件把那條原則推到底，看它會改變什麼。

## 一、原則在 6 種事件裡有 5 種成立

| 事件 | 對倒數做什麼 | ＝需要補擦？ |
| --- | --- | --- |
| 大量流汗 | 期限拉到事件當下 | ✅ |
| 擦毛巾 | 期限拉到事件當下 | ✅ |
| 明顯摩擦 | 期限拉到事件當下 | ✅ |
| 洗手 | 期限拉到事件當下（只有手部） | ✅ |
| 離水 | 期限拉到事件當下 | ✅ |
| **游泳／下水** | **開啟水中區間，改用耐水規則** | ❌ |

前五個是**損耗**——防曬掉了，所以要補。下水是**區間**——不是損耗，是「接下來這段時間改用另一套計時」。

**所以「記錄狀況」這個選單裝了兩種不同的東西。** 它用一個中性的容器名（「發生了什麼？」）把「你該補擦了」與「計時規則變了」混在一起，這是流程讀起來怪的根源。

## 二、已實測的地雷：事件與補擦不得同一時間戳

合併流程時最容易寫成「同一個時間戳送出兩件事」。**那會讓補擦失效。**

`reducer.ts` 判斷損耗事件還算不算數的條件是 `事件時間 >= 最新塗抹時間`——是 `>=`，所以時間相同的事件**依然成立**，期限被拉到那一刻。

用 `packages/domain` 的純函式實測（2026-09-02）：

| 情況 | eventTriggeredDeadline | zoneDueAt | timingStatus |
| --- | --- | --- | --- |
| 事件與補擦同一時間戳 | `10:30` | `10:30` | **`reapply_due`** |
| 補擦晚一分鐘 | `null` | `12:31` | `tracking` |

第一列就是「補完立刻又到期」。實作時**事件必須嚴格早於塗抹時間**，而且要有測試釘住這個邊界。

## 三、原則沒涵蓋的兩種情況（必須保留出口）

1. **夜間**：UV 為 0 時主行動是「結束提醒」（`2026-08-26-night-session-layout-revert.md`）。這時流汗不需要補擦，硬導向補擦是噪音。
2. **想補但補不了**：沒帶防曬乳、還在水裡、手上都是沙。這時只記錄事件是對的——倒數要反映現實，而不是假裝沒事發生。

所以合併之後仍需要「現在還不能補擦，只先記錄」這條路。**這不是例外處理，是產品誠實度的一部分。**

## 四、目標形狀

單一流程，主要產出是一次補擦：

```
入口：該補擦了／記錄補擦
  1. 為什麼補擦？   時間到了／流汗／擦毛巾／摩擦／洗手／離水
  2. 哪些部位       由原因決定預選
  3. 用哪罐、什麼時間
  送出 → 同時寫入損耗事件與補擦
出口：現在還不能補擦，只先記錄 → 只寫入損耗事件
```

「游泳／下水」離開這個選單——它不是補擦的原因。落點見第六節。

## 四之二、CTA 的第一個落地（2026-09-02 已實作）

### 改了什麼

`tracking` 的主行動由 `report_context_event` 改為 `record_reapplication`。

### 為什麼

改動前，一切正常時 App 唯一叫使用者做的事是「去宣告一個問題」。而實際後果比
語意問題更嚴重：首頁只有一顆按鈕、`secondaryActions` 是空的，所以**還沒到期就
沒有辦法記錄補擦**。提早補擦是常見的（要再出門、快下水、覺得乾了），核心動作
在正常狀態下不可達說不過去。

UI 其實早就不同意 domain 的說法：2026-08-30 已把「記錄狀況」從深杏桃主 CTA 降級
成提問卡。這次是讓 domain 跟上那個判斷。

舊版 P0 決策表把 tier 70 寫成 `report_context_event`，但那份在
`docs/archive/2026-08-pre-redesign/`，依 CLAUDE.md 只能用來理解歷史。

### 連帶：提問卡變成獨立入口

提問卡原本綁在 `actionKind === "report_context_event"`，domain 一改它就會整個
消失——記錄狀況會沒有入口。所以條件改成「倒數正常跑著」，卡片裡的按鈕明確導向
記錄狀況，不再跟著主行動走。

**不變式：畫面上永遠恰好有一個可按的行動。** 第一版的隱藏規則下得太粗，在
「到期又是記錄狀況」時會讓提問卡與 CTA 同時消失；被 HomePage 既有的守門接住
（那條 2026-08-30 才為了拆開 actionKind 與 tone 兩個變因而加）。現在有一條測試
直接把這個不變式講明白。

## 四之三、暫停提醒：不做（2026-09-02 使用者裁決）

使用者問過「要不要把暫停提醒也變成按鈕（例如兩小時內回到不需要補擦的空間，
像計時器那樣）」。查證之後**不做**，改用既有的「結束提醒」。

### domain 目前沒有暫停這個概念

- `TrackingStatus` 只有 `active | ended`，沒有 paused
- `context_changed`（進入室內／返回戶外）在 reducer 裡被直接略過，對倒數零影響
- 沒有任何 indoor 概念

### 更根本的：期限是絕對時刻，不是累積曝曬

`generalDueAt = appliedAt + interval`。要「暫停」等於改核心計時模型，不是加一顆
按鈕。衣物遮蔽看起來像暫停，其實只是不顯示——再外露時期限仍然從原本的
`appliedAt` 算起。

### 而且方向危險

暫停會讓提醒**變晚**，等於 App 主張「室內時間不算」。這比 App 目前的立場強——
它現在明說「不是安全曝曬時間或防護效果保證」。這是健康相關主張，要有依據才能
做，不能當成 UI 便利。

### 替代

「結束提醒」已經存在，而且更誠實：回到戶外時本來就該重新塗抹，開新 session 剛好
對應現實。若日後仍要處理「在室內時別一直吵我」，正確的切法是**暫停通知而不暫停
倒數**——那是呈現層的事，不動期限、不做健康主張。

## 五、實作路徑

### 交易邊界：兩段交易就夠，不需要新的合併命令

`planContextEvent` 與 `planReapplication` 是兩個 planner，`reportContextEvent` 與 `reapply` 是兩個各自帶交易的 repository 方法。合併命令要動 contracts、domain、persistence 三層。

**不需要。** 依序送出兩個命令即可，理由是**中間狀態本來就是合法的**：「記錄了事件、還沒補擦」正是現在的產品狀態，也是第三節那條出口要的狀態。第二段失敗時使用者落在一個有意義的地方，不是半筆爛帳。

這跟一般的多步寫入不同，值得寫進註解——否則下一個人會以為這裡缺一個交易。

## 五之三、階段二的落地（2026-09-03）

首頁的「剛才有流汗、碰水或擦拭嗎？」提問卡**移除**，記錄狀況改由補擦流程裡的
出口進入：`ReapplyReasonPicker` 底部的「現在還不能補擦，先記錄狀況」。

那張卡是 2026-08-30 把記錄狀況從主 CTA 降級時留下的獨立入口。按「遇到了事件
＝需要補擦」的原則，它讓同一件事有兩個並列入口，而其中一個把使用者導離主線。

### 記錄狀況沒有被拿掉

它在**真的是主行動時**仍然是主 CTA——例如遮蔽狀態下補擦不適用，記錄狀況就是
唯一能做的事。降級的是「與補擦並列的獨立入口」，不是這條流程本身。

守門也照這兩個方向分開寫：一條擋提問卡回來，一條擋降級做過頭變成拿掉。

### 出口是文字連結，不是按鈕

依 2026-08-31 的裁決：次要動作用文字連結，實心按鈕是主行動的語彙。這裡的語意
是「這條路不適用」，不是一個與五個原因並列的第六個選擇。

### 副作用：離水的入口變深了

「離水」只存在於記錄狀況流程（階段一刻意不收它——它會關閉一段水中區間，是狀態
轉換不是註記）。移掉提問卡之後，想單獨記一筆離水的人得先進補擦流程再岔出去。

**不擋倒數正確性**：`water_end` 沒記，`activeWaterDeadline` 仍會照耐水分鐘數
到期，不會卡在水中狀態。這是「多走一步」，不是「做不到」。

### 元件不換頁

`ReapplyReasonPicker` 只 `emit("exit")`，導航留在 `ReapplyPage` 的
`goToReport()`。守門分兩半：元件那半用掛載測試，頁面接線那半掃原始碼
（掛整頁要造很大的 services mock），掃描前先剝註解、比對完整屬性。

## 五之二、階段一的落地（2026-09-02）

補擦流程最前面加上「為什麼補擦？」：時間到了（預設）／大量流汗／擦毛巾／
明顯摩擦／洗手。選了原因就在補擦之前先送出一筆損耗事件。

**「離水」刻意不在選項裡。** 它不只是一個原因，還會關閉一段水中區間（需要
`activityIntervalId`），那是狀態轉換不是註記。它留在「記錄狀況」流程，而那條
路自 #108 之後本來就能直接接著補擦。

### 時間戳

事件時間 = 塗抹時間 − 1 分鐘。**不是美觀考量**：第二節那個實測地雷就是同一
時間戳會讓補擦立刻又到期。往前挪也符合現實——先流汗，才去補擦。

### 兩段交易的重試

第二段（補擦）失敗後重試時**不會重新送出事件**：控制器記著事件已提交後的
revision。沒有這一步會寫出兩筆流汗。補擦命令也改用事件之後的 revision，
否則第二段必然撞 REVISION_CONFLICT。

### 實機驗證時發現的既有問題（已於 2026-09-02 修復）

端到端跑完之後，事件與塗抹的時間順序是對的（塗抹 12:53 → 流汗 12:54 → 補擦
12:55），但**該部位仍然停在 `reapply_due`**。

根因不在時間戳，在 `latestEligibleApplicationForCause`：它只採計
`ruleEligibilityAtApplication === "eligible"` 的塗抹。而 causeEvents 的過濾是

```
latestEligibleForCause === null || 事件時間 >= 最新合格塗抹.appliedAt
```

**一筆合格塗抹都沒有時，`null` 讓所有損耗事件無條件成立。** 也就是說：

> 標示未確認的使用者，只要記錄過任何損耗事件，該部位就會永遠到期——補擦也清不掉。

用 `packages/domain` 的純函式確認過（未確認標示 ＋ 流汗 10:30 ＋ 補擦 10:31 →
`eventTriggeredDeadline` 仍是 10:30、狀態仍是 `reapply_due`）。

這與 2026-08-30「未確認標示改用 120 分鐘保守預設、不再擋住倒數」的裁決不一致：
那筆塗抹**足以開始一段倒數，卻不足以清掉一個原因**。

**不是這次改動造成的**：舊的兩段式流程（記錄狀況 → 記錄補擦）產生的事件完全
相同，結果也相同。階段一只是讓它更容易被遇到。

#### 修法（已套用）

判準由「最後一次 `eligible` 的塗抹」改為「最後一次**沒有被
`blocksGeneralDeadline` 擋住**的塗抹」，函式一併更名為
`latestCauseResettingApplication`。

原則：**足以開始一段倒數的塗抹，就足以清掉一個原因。** 兩件事從此共用同一個
閘門，不會再出現「這筆塗抹算數也不算數」的分裂。

被擋住的三種（過期／回報異常／回報不適）**維持不能清**——那是 S-11／S-13 明訂
無法直接恢復的安全封鎖，拿一瓶過期的防曬乳再擦一次不該讓警示消失。耐水期限也
不走這裡，仍然要求 `eligible`。

實機驗證（標示未確認的預設路徑）：流汗 13:17:23 → 補擦 13:18:23，部位狀態
`tracking`、下次到期 15:18:23（＝補擦 ＋ 120 分鐘保守間隔）。修復前是永遠
`reapply_due`。

### 已驗證

實機跑過完整流程：版面正確（五個選項、預設選中「時間到了」、沿用共用的選取
樣式），兩筆事件依序寫入 IndexedDB，時間戳為塗抹 12:53 → 流汗 12:54 → 補擦
12:55。行為另有六條破壞驗證過的單元守門。

## 六、尚未解決：下水要搬去哪

`context_changed`（進入室內／返回戶外）走的是另一條命令路徑，**介面上目前沒有任何出口**。也就是說「游泳／下水」現在是 session 中途開啟水中區間的唯一方法。

直接把它從選單拿掉會讓那個能力消失。可能的落點：

1. 首頁加一個「目前情境」區塊，把下水與進入室內／返回戶外一起放進去（同時補上 `context_changed` 缺的介面）
2. 維持在同一頁但明確分區：「你該補擦了」與「情境改變了」兩組，不再混在一張清單

**第 1 個比較貼合原則，但範圍大很多**（等於補一塊還沒做的功能）。這一項需要另外裁決，不要夾帶在重構裡。
