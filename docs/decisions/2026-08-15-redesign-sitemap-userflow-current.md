## 一、產品核心與基本原則

- 核心目標是防曬乳補擦倒數，不是過往紀錄、衛教閱讀或裝備收藏。
- 使用者可以不註冊直接使用；本機資料優先保存。
- 同一裝置只允許一個活動 Session；同一裝置多分頁同步同一 Session。
- Session、倒數與通知不因使用者前往衛教或「更多」而暫停。
- 通知、PWA、網路與瀏覽器能力不足時，仍不得阻擋本機倒數與手動操作。
- 衛教內容採「防曬氣象管家 × 防曬生活編輯部」的混合方向；提醒頁保持任務導向，衛教頁才使用較完整的編輯設計。
- 舊版四個下排入口、`/learn` 公開路徑與舊首頁／提醒分工，均已被目前三入口、`/education` 公開衛教與根網址提醒方案取代；舊文件保留但不作為 wireframe 依據。
- **`/help` 系列與 `/special-situation` 保留**（2026-08-23 裁決，取代本文件先前「已被取代」的記載）。它們不是 `/education` 的重複入口：目前 `/education` 是唯一有內容的，另兩者的內容仍在審查中，實際是「一個有內容的門加兩扇鎖住的門」。另有功能相依——`/help/how-it-works` 同時是時鐘不可信且離線時 `view_conservative_reminder` 的降級落點，移除會讓該路徑無處可去。見 `2026-08-23-content-and-flow-decisions.md` §一。

## 二、現行 Sitemap

### 2.1 App／PWA 主要入口

根網址 `/` 直接進入「提醒」頁：

- 沒有活動 Session：顯示「開始防曬提醒」入口。
- 有活動 Session：直接顯示目前倒數。

下排導覽固定三項：

1. **提醒**：核心倒數、部位狀態與補擦操作。
2. **裝備**：防曬乳與其他防曬裝備的紀錄。
3. **更多**：衛教、問題回報、通知、資料與關於等支援功能。

不再保留獨立的「首頁」下排入口，也不新增衛教專用下排入口。

### 2.2 提醒相關畫面

- `/`：提醒主入口。
- `/setup/context`：開始提醒步驟 1，設定情境。
- `/setup/timing`：開始提醒步驟 2，設定塗抹時間、部位與必要摘要，直接完成開始提醒。
- `/reminder`：進行中的提醒與完整狀態。
- `/reminder/reapply`：記錄補擦；仍需在 wireframe 階段確認最終顯示形式。**這是 wireframe 應最優先繪製的畫面**——它是使用頻率最高的動作與整個產品的閉環，卻是唯一未定案的核心動作；相對地，分享圖片、跨裝置同步等低頻功能反而已有完整規格。
- `/reminder/report`：回報狀況；納入流汗、碰水、淋雨等事件。
- `/reminder/event/:id/correct`：更正最近事件。
- `/region`：地區與定位設定。

原本獨立的 `/setup/review` 不再作為現行流程；其內容併入步驟 2。

開始提醒設定採同一流程內完成，不因產品標示、部位調整或通知設定跳離到平行頁面；必要的調整以同頁區塊或 sheet 呈現。

### 2.3 裝備

- `/products`：防曬裝備清單。
- `/products/new`：新增裝備，先選品類。
- `/products/:id/edit`：編輯裝備。

品類分為：

- 防曬乳：會影響補擦倒數。
- 防曬衣物：依使用方式部分影響防護狀態。
- 太陽眼鏡、帽子、陽傘、其他裝備：純紀錄，不影響倒數。

裝備頁沒有紀錄時，主入口為「新增第一件防曬裝備」；不要求先建立裝備，也不阻擋從提醒頁開始使用。

新增裝備採同一頁動態表單：先選品類，再顯示對應欄位；每類最低只要求裝備名稱，其餘資料可稍後補充。

- 從開始提醒流程新增防曬乳：建立後直接套用到本次提醒。
- 從裝備頁新增防曬乳：只建立紀錄，不自動替換目前產品。
- 編輯目前使用中的防曬乳：本次 Session 保留建立時的產品快照，修改只影響之後的新 Session。
- 刪除目前使用中的防曬乳：允許刪除；本次 Session 仍保留原產品快照。
- 點擊裝備卡片進入詳情頁，再由詳情頁進入編輯、分享或刪除。
- 分享圖片預設只放產品／品牌名稱、照片與使用心得；價格、購買日期、尺寸由使用者選擇，私人備註預設不分享。
- 標示資料尚未完整的防曬乳仍列在「目前使用」，顯示「標示尚未確認」；可使用 120 分鐘保守預設。

### 2.4 更多

「更多」頁使用統一卡片網格：桌面 2 欄、手機 1 欄。所有入口卡尺寸、圖示位置、圓角與文字結構一致，僅使用淡色分隔或小字提示做輕量分組。

入口排序採以下優先順序：

1. 通知設定
2. 防曬衛教
3. 本機資料與隱私
4. 問題回報與意見回饋
5. 安裝到主畫面
6. 說明與關於

「通知設定」卡片顯示簡短狀態。可用的狀態受實際通知能力限制，見 §4.3。

六張入口卡對應的實際路由：

| 入口卡 | 路由 | 備註 |
| --- | --- | --- |
| 通知設定 | 尚未建立 | 通知功能 2026-08-23 才裁決實作，設定頁待 wireframe |
| 防曬衛教 | `/education` | 唯一有內容的衛教入口 |
| 本機資料與隱私 | `/settings/data` | 另有 `/settings/sync`、`/settings/account-data` |
| 問題回報與意見回饋 | `/feedback` | |
| 安裝到主畫面 | `/install` | |
| 說明與關於 | `/help` | 含 `/help/beach`、`/help/how-it-works` |

`/special-situation` 保留但目前不在六張卡的排序內；內容通過審查前顯示「此功能尚未開放」。

通知設定與本機資料與隱私都採單頁分區；本機備份放第一層，Google 同步放次要區塊。問題回報與意見回饋共用一個表單，先選回報類型；不需登入，聯絡信箱選填。

第一次使用時可在免登入入口旁提供次要 Google 登入／同步入口；完整同步設定仍可從本機資料與隱私進入。第一次同步前顯示資料預覽，敏感資料預設不傳；衝突由使用者比較後選擇版本；關閉同步只停止未來同步，既有雲端資料保留。

頁尾另放版本、隱私政策、使用條款與資料說明，不做成功能卡片。

## 三、公開衛教 Sitemap

公開衛教使用獨立 `/education` 區域；根網址與 PWA 仍以提醒為核心。

- `/education`：衛教首頁。
- `/education/{category-slug}`：六個公開分類頁。
- `/education/articles/{article-slug}`：公開文章頁，文章 URL 不綁定分類。
- 不存在的分類或文章使用衛教專用 404 頁。

六個分類 slug：

1. `uv-basics`：了解今天的 UV
2. `before-going-out`：出門前準備
3. `reapply-sunscreen`：外出中的補擦
4. `sweat-and-water`：流汗或碰水後
5. `after-sun-care`：回家後與皮膚照顧
6. `special-situations`：特殊情況

公開頁可被搜尋引擎索引；搜尋查詢、情境篩選與收藏結果不建立公開 URL、canonical 或 sitemap 項目。

PWA 內的文章保留下排導覽與收藏操作；一般瀏覽器、搜尋或外部分享進入時使用獨立公開閱讀版面，不顯示收藏、Session、產品、位置或其他個人資料。

## 四、主要 User Flow

### 4.1 第一次使用與開始提醒

1. 使用者進入 `/`。
2. 點擊「開始防曬提醒」。
3. 在同一個設定流程完成步驟 1 情境與步驟 2 塗抹時間、部位與摘要確認。
4. 點擊「開始提醒」後立即建立 Session 並開始倒數。
5. 通知權限在此時詢問；允許或拒絕後都直接開始，不增加第二個確認頁。
6. 若通知未開啟、平台不支援通知或目前離線，仍允許倒數，並在倒數區附近顯示小型狀態提示。提示內容須符合 §4.3——說明送達限制，並讓使用者知道自己仍需回來查看。

### 4.2 進行中的提醒

- `/reminder` 顯示完整部位狀態、補擦操作、最近事件與結束控制。
- 進行中的 Session 離開提醒頁後仍持續倒數與通知。
- 其他頁面不顯示迷你倒數或 Session 狀態，避免產生第二個提醒頁。
- 已有活動 Session 時，再次按「開始防曬提醒」只顯示目前提醒與「回到目前提醒」，不建立第二個 Session。

#### 夜間與收工行為

**本節 2026-08-23 補入。** 這些行為在程式碼中已實作並有測試，但先前未寫進本基準，重畫 wireframe 時容易整個漏掉。

**夜間依「是否有進行中的 Session」分成兩個畫面**，主要行動不同（2026-08-23 確認）：

| 狀態 | 主要行動 | 實作 |
| --- | --- | --- |
| 夜間 ＋ 有 Session 進行中 | **結束提醒**（收工），不讓倒數跨夜 | `NightWindDownPrompt.vue`（含測試） |
| 夜間 ＋ 沒有 Session | **無主要 CTA**，改以說明告知現在不需要防曬 | 次日預報提示 `EveningUvPrompt.vue` |

第二種狀態刻意不提供開始倒數的主要按鈕——夜間 UV 為 0，不需要防曬。但必須：

- 補一句說明「為什麼現在沒有事情要做」，否則使用者無法判斷是功能壞了還是本來就沒事做。
- 保留一個安靜的逃生出口（text link，非按鈕）。硬性阻斷會讓時區設錯、跨時區旅行或夜班戶外工作者無法使用產品。

兩者都不自動結束 Session——決定權仍在使用者。文案細節見 `2026-08-23-wireframe-copy-fixes.md` §3.3、§3.4。

原始裁決 `2026-08-08-night-behavior.md` 位於 `docs/archive/2026-08-pre-redesign/decision-history/`，屬歷史資料；行為描述以本節為準。

#### 不提供使用者主動暫停

**本節 2026-08-23 補入取捨理由。** 系統只有「結束」，沒有使用者主動「暫停」。

（§一提到的「不因前往衛教或更多而暫停」是另一件事，指切換頁面時倒數不中斷。）

實際情境是中午進室內用餐一小時，使用者只能選擇讓倒數繼續（不準）或結束再重設（麻煩）。團隊已評估並否決暫停功能，理由是：

> 暫停後恢復會讓 12 小時前的防曬顯示成「還有 40 分鐘」。

這是正確的取捨——暫停會破壞資料正確性。但此前理由只存在於 `NightWindDownPrompt.test.ts:61` 的註解，規格未記載，導致同一提案反覆出現。記錄於此後**不需要再提案**。

### 4.3 通知與離線

**本節 2026-08-23 全面改寫。** 先前版本描述的「背景通知」在程式碼中從未存在，且假設通知可在分頁關閉後送達——那在 web 平台上做不到。改寫依據見 `2026-08-23-notification-decision.md`。

#### 實際能力

本機通知（service worker ＋ `showNotification`），**不含後端 Web Push**。

| 情境 | 是否送達 |
| --- | --- |
| 分頁在前景 | 送達 |
| 分頁仍存活但已切到其他 App 或分頁 | 送達 |
| 瀏覽器完全關閉 | **不送達** |
| 分頁被系統回收（行動端常見） | **不送達** |

這是平台限制不是實作缺陷：Notification Triggers（`TimestampTrigger`）已被 Chrome 放棄且從未進 stable，Safari 只支援 push 不支援本機通知。

#### 畫面必須誠實說明限制

因為送達無法保證，**任何提到通知的畫面都必須讓使用者知道自己仍需回來查看**。省略這句會讓產品退回「規格承諾、實作交付不了」的狀態，那正是 2026-08-23 盤點要解決的問題。

**不使用「背景通知」一詞。** 目前沒有背景通知，用這個詞會讓使用者誤以為關掉瀏覽器仍收得到。

#### 狀態

- 尚未詢問：於建立提醒時詢問一次（§4.1 第 5 點）。
- 已拒絕：顯示「通知未開啟」與瀏覽器設定引導；本機倒數不受影響。
- 已允許：顯示已開啟，並同時說明送達限制。
- **平台不支援**（非安全來源或瀏覽器不具備能力）：與「已拒絕」分開處理。使用者無從授權，引導他去瀏覽器設定沒有意義，文案必須不同。
- 離線：顯示「目前離線」。本機倒數與本機通知都不需要網路，照常運作。

#### 排程規則

- 只排**一則**通知，對應 `sessionNextDueAt`，不替 16 個部位各排一則——使用者要做的動作只有一個。
- Session 結束或下一個到期時間消失時清空排程；留著會在使用者已經補擦之後才跳通知。
- 不補送錯過的通知。

#### 通知設定頁

單頁分區：狀態 → 送達限制說明 → 再次提醒頻率 → 裝置測試。

**先前規劃的「聲音與震動」移除**——那由作業系統控制，web 端無法設定。

### 4.4 多分頁

- 同一裝置多分頁同步同一活動 Session。
- 任一分頁補擦、停止部位或結束 Session，其他分頁同步更新。
- 舊分頁重新連線發現 Session 已結束時，顯示「本次提醒已結束」與「開始新的防曬提醒」，不恢復舊倒數、不自動建立新 Session。

### 4.5 衛教瀏覽

1. 使用者從「更多」進入 `/education`。
2. 衛教首頁顯示編輯部主題導讀與六個分類；「了解今天的 UV」為大卡片並標示「先從這裡開始」。
3. 進入分類頁後先看到分類主模組，再看到 1 篇編輯推薦與 2 篇延伸閱讀。
4. 點擊「查看全部」進入獨立分類文章列表頁；列表使用兩欄卡片網格，第一版一次顯示全部文章。
5. 點擊文章後在目前頁面開啟；返回時盡量保留原分類位置、展開狀態、篩選與捲動位置。
6. 文章內頁提供麵包屑、可展開段落目錄、資料來源與審閱資訊、2 篇相關文章與回到分類入口。

### 4.6 衛教分類主模組

- **了解今天的 UV**：教育型 UV 色階、一日強度曲線、主問答與延伸問答；不依賴即時定位或即時 UV。
- **出門前準備**：編輯部階梯卡，選擇防曬乳 → 塗抹 → 準備裝備；不做勾選清單。
- **外出中的補擦**：補擦節奏線為主，抽象七部位示意與四張生活情境卡為補充。
- **流汗或碰水後**：直向三步流程「發生什麼情況 → 先做什麼 → 何時補擦」，使用編號、細連線與小圖示。
- **回家後與皮膚照顧**：直向三步流程「清潔防曬 → 觀察肌膚狀況 → 基本照顧」；不適狀況以短提示連到特殊情況。
- **特殊情況**：只涵蓋防曬／日曬相關肌膚反應，使用簡短安全判斷流程，不作疾病診斷或求助分級。

## 五、整合結論與 wireframe 前檢查

目前核心 Sitemap 與 User Flow 已形成共同理解；後續不再重問已確認的產品決策。剩餘工作屬於 wireframe 與文案層級：

- 將各頁的按鈕、空狀態、錯誤狀態與返回入口逐頁列成 wireframe 規格。
- 統一「開始提醒」「記錄補擦」「不再提醒這個部位」「換新的一瓶」等操作文案。
- 逐頁確認鍵盤、手機、PWA、離線與公開文章外框的狀態。
- 開發前重新檢查公開 `/education` 路徑、canonical 與 sitemap；`/learn` 已不存在於路由。
- **`/help` 不再列為待移除**（2026-08-23 裁決，見 §一）。仍需確認的是內容層：`/help` 兩則主題的正文尚未接進 App，且 `/help/how-it-works` 的原文描述了不存在的通知能力，必須依 §4.3 改寫後才能發布。

本文件目前是 wireframe 的唯一現行基準；舊文件不刪除，但只作為歷史參考。仍不修改程式碼。

## 六、Sitemap／User Flow 呈現格式

正式整理與簡報呈現採用接近參考圖的純文字樹狀結構：

- Sitemap 拆成兩份：
  1. App／PWA Sitemap
  2. 公開衛教 Sitemap
