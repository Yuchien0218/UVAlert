# 行距收斂：body 文字 1.7 → 1.75 → 1.7 → 1.6（使用者連續調整）

**日期**：2026-08-25（Asia/Taipei），同日三輪
**狀態**：已完成。**目前最終值是 1.6**——見下方時間軸，本文件標題保留完整調整史，不要只看標題數字。
**裁決**：全域 `body` 行高與全站同一批約 38 個檔案，跟著使用者三次回饋依序調整：1.7 → 1.75（對齊 DESIGN.md 配套值）→ 1.7（使用者回饋「再縮小一點點」）→ 1.6（使用者再次要求「再改成 1.6」）。`DESIGN.md` 第三節 Body MD 那列同步跟著回寫，目前是 1.6。
**影響範圍**：`packages/ui/src/styles.css`（全域預設）＋ 38 個檔案，三輪都是同一批檔案。

## 背景與根因

使用者反映「行距、行與段落間距怪怪的」。查下來根因跟今天稍早的字級收斂是同一條因果鏈：

1. 今天稍早把 `--font-size-body` 從 14px 調到 16px，對齊 `DESIGN.md` 的 body-md 目標（見 [[2026-08-25-typography-token-consolidation.md]]）。
2. 但 `DESIGN.md` 第三節「中文間距覆寫」把行高跟字級**配對**訂定：Body MD（16px）→ 1.75；Body SM（14px，僅細則）→ 1.7。字級調整那次沒有連帶調行高。
3. 結果是內文字變大了，但行距還停在舊字級（14px）配的 1.7，讀起來行與行擠壓感變重——這正是「怪怪的」的來源，不是憑空的美感問題。

盤點全站 `line-height` 用量，發現這個問題被放大：`line-height: 1.7` 在 72 處被逐字重複寫死（多數是複製既有段落樣式時帶過去的），而不是統一套用一個 token。改身度時如果只改全域 `body{}` 一處，這 72 處覆寫會維持在舊值，反而製造出「有的段落 1.7、有的 1.75」的新落差。

## 套用的變更

1. **全域**：`packages/ui/src/styles.css` 的 `body { line-height: 1.7 }` → `1.75`。
2. **批次收斂**：38 個檔案裡逐字重複的 `line-height: 1.7;` 全部改成 `1.75`（用 `sed` 批次處理，而非 70+ 次手動編輯；處理前已確認這批清一色是內文段落角色，不是標題／讀數／按鈕等已有獨立行高的角色）。
3. **修正誤蓋**：批次處理連帶蓋到 2 處 label 級（12.8px）文字——`QuickProtectionSummary.vue` 的 `.quick-protection__note`、`FiveDayUvCard.vue` 的 `.uv-forecast__source`／`.uv-forecast__note`——這兩處改回 **1.5**，對齊 `DESIGN.md`「說明／標籤」該有的行高，而不是回退到原本也不精確的 1.7。
4. **拉平離群值**：`EducationArticlePage.vue` 的 `.education-article-summary`（1.8→1.75）與 `InstallPage.vue` 的 `.install-card ol, .limits ul`（1.8→1.75），兩者跟同頁其他同角色段落（都是 1.75）沒有理由不同，收斂掉。

## 刻意不動的部分

- `EducationArticlePage.vue` 的 `.education-article-body`（衛教文章正文容器，行高 1.85）——**刻意維持更寬**，不跟其他段落收斂到 1.75。理由：這是長篇連續閱讀的正文容器，比起卡片／通知框裡的一兩句導言，長文本給更寬的行距是常見且合理的編輯判斷，不是同一個角色的重複值。
- 標題（`.education-article-body :deep(h2)` 1.35／`:deep(h3)` 1.45）、大讀數（`.stat-figure` 0.95）、頁面主標（`.page-heading__title` 0.98）、徽章／按鈕（`.zone-chip` 1.4、按鈕 1.2）——這些本來就是跟字級成對、刻意更緊的獨立角色，不屬於這次「內文段落」的收斂範圍。
- **段落間距（margin／gap）沒有發現寫死問題**：檢查過全站 margin-top／margin 簡寫，全部已經套用 `--space-N` token，沒有裸寫的 px／rem 數字。`--space-stack-title-body` 等語意別名目前使用率低（只有 1 處），但這是命名層級的問題，不是「寫死」問題，不在這次範圍內。

## 第二輪：使用者確認改回 1.7

第一輪的 1.75 是照 `DESIGN.md` 文件訂的配對值推算出來的，**不是使用者實際看過畫面後確認的結果**。使用者回饋「p 的行距再縮小一點點」後，把這 38 個檔案的 `line-height: 1.75` 全部改回 `1.7`（`.education-article-body` 的 1.85 長文本容器不受影響）。

## 第三輪：使用者要求再改成 1.6

使用者接著直接要求「再改成 1.6」，同樣的 38 個檔案 + 全域預設一起改成 `1.6`。批次 `sed` 處理時發現第二輪留在 `styles.css` 註解裡的一段調整史文字，因為逐字含有 `line-height: 1.7` 字串，被 sed 誤改成 `1.6`（純文字說明被當成程式碼改到）——已重寫整段註解修正，順便把四輪歷史一次記清楚。**這是這次操作學到的教訓：批次 sed 改值之前，要留意目標檔案裡有沒有「用文字描述舊數值」的註解，那些不該跟著程式碼一起被取代。**

`DESIGN.md` 第三節 Body MD 那一列同步回寫成 1.6。

## 驗證

`pnpm check`（typecheck + 78 個測試檔、466 筆測試）全數通過，三輪都跑過。批次 `sed` 處理過程中順手確認過 git diff：雖然這批檔案的工作目錄行尾是 LF（不是 CRLF），git 顯示的警告訊息是既有狀態，不是這次操作造成的，實際 diff 乾淨、只改動目標那一行，沒有整檔案行尾重寫的污染。

~~**未經瀏覽器視覺驗證**~~——**2026-08-29 已補驗，見下節。** 當初的顧慮是：1.6 是三次調整裡最緊的一版，中文內文在這個行高下的可讀性沒有實際看過畫面。

## 2026-08-29 視覺驗證結果：通過，但有一個觀察

實測卡片與導言段落行高為 **25.6px / 16px = 1.6**，與文件一致。走過首頁、`/products`、`/settings/data`、`/setup`、衛教文章頁，中文內文在 1.6 下**讀得清楚，沒有擠壓感**。

**觀察**：衛教文章頁上會同時看到兩種行高——導言 `.education-article-summary` 是 1.6，正下方的正文 `.education-article-body` 是刻意保留的 1.85。兩者相鄰時 1.6 看起來明顯比較緊。這不是錯誤（長文本容器給更寬行距是當初刻意的判斷），但如果之後有人覺得「導言怪怪的」，原因會是這個對比，不是 1.6 本身有問題。
