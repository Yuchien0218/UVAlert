# B9 Icon-first 與說明文字漸進揭露設計規格

**日期**：2026-08-27（Asia/Taipei）

**狀態**：**icon-first 已完成並上線；漸進揭露的推行已於 2026-08-29 結案，不再推第三輪。** 分類規則（§3）與互動契約（§4）繼續有效，收掉的是「系統性把既有說明文字改成可展開」這件事——見 §八。

**範圍**：以 icon 建立第一視覺錨點、降低常駐說明文字量、定義可展開說明的互動與無障礙契約；不納入 B8 字級實作

## 一、問題與設計方向

目前部分畫面讓功能名稱、狀態、原理與補充說明同時常駐，每個區塊視覺重量接近，造成畫面壅擠。部分 icon 又偏小，只能成為文字附件，沒有形成清楚的掃讀入口。

採用已確認的方案 B：**一行必要標題＋按需展開說明**。icon 是第一視覺錨點，文字仍負責名稱與決策資訊；不採完全只剩 icon 的方案。

> **⚠ 2026-08-29 結案更正**：上面「造成畫面壅擠」的前提，經兩輪逐項分類**沒有得到證據支持**。這個產品的說明文字密度高，是因為它在講健康邊界與不可逆操作，不是因為囉唆。詳見 §八。

## 二、icon 尺寸角色

**2026-08-29 更正**：本節原本列的 18px 檔位已否決，Lucide 也已從專案移除。以下是現行的四檔位（`DESIGN.md` 第八節為權威）：

| 尺寸 | 用途                                              |
| ---: | ------------------------------------------------- |
| 16px | 文字內嵌、極次要的標記                            |
| 20px | 文字旁的輔助 icon，不主導區塊                     |
| 24px | 導覽、按鈕、設定列的主要 icon                     |
| 32px | 卡片或功能入口的主要視覺                          |
| 44px | `--tap-target` 最小操作範圍；**不是** icon 圖形尺寸 |

**18px 已否決**（B9 裁決 1，2026-08-29）：只加 32 檔位，不新增中間值——級距太密會讓「這裡該用哪一個」變成每次都要重新判斷。

不再有「不能破壞既有 Lucide 線寬」的約束——`@lucide/vue` 已於 2026-08-29 完全移除。自訂圖示線寬固定 2.5、隨 viewBox 等比縮放，放大到 32px 不會有線寬問題。

大型狀態或品牌插圖不直接套入這些 UI icon 尺寸，需另有元件規格。

## 三、資訊分層

### 必須常駐

- 功能或設定名稱。
- 目前狀態、已選值、數量或會直接影響操作判斷的資訊。
- 錯誤、驗證訊息與必填條件。
- 不可逆操作的後果與健康／安全相關限制。
- 使用者採取動作前必須知道的條件。

### 可以按需展開

- 功能原理與「為什麼需要」的背景。
- 較長的使用範例或進一步解釋。
- 不影響當下決策的補充內容。
- 已被標題與狀態充分表達的重複說明。

不能以「縮短畫面」為理由，把健康內容的來源、審閱狀態、警告後果或表單錯誤藏起來。

## 四、互動契約

- 優先使用明確的資訊按鈕或可展開整列；同一種元件只能採一種一致模式。
- 控制項使用真實 `button`，設定 `aria-expanded` 與 `aria-controls`，可用 Enter／Space 操作。
- 展開後說明緊鄰其所屬項目，不使用離開上下文的全域 modal。
- 收合不清除使用者輸入、選擇或目前狀態。
- 重要內容不能只放在 hover tooltip；觸控裝置、鍵盤與螢幕閱讀器必須取得同等資訊。
- icon-only 操作必須有可存取名稱；不常見或具風險的操作仍需可見文字。

## 五、導入方式

> **⚠ 2026-08-29：本節的推行計畫已結案。** 下面的方法本身是對的，而且正是用它得出「不要做」的結論；但「逐頁找候選說明文字」這個動作**已經做完兩輪，證據充分，不需要第三輪**。見 §八。

B9 必須先逐頁列出候選說明文字，依「常駐／可展開／不可隱藏」分類，再改元件。不進行全站批次刪文，也不只靠字數決定是否收合。

第一輪優先考慮資訊密度較高、重複說明較多的設定與摘要畫面；核心提醒流程、錯誤狀態及健康內容先維持完整可見。每次導入需比較展開前後的理解程度、操作步數與版面高度。

## 六、驗證契約

- 針對收合／展開、鍵盤操作、焦點、`aria-expanded` 與狀態保存撰寫互動測試。
- 在 390px 行動版確認 icon、標題、狀態與控制不互相擠壓，且點擊範圍至少 44px。
- 在桌面版確認 icon 放大後沒有形成過多競爭焦點。
- 以 200% zoom 與螢幕閱讀器語意檢查內容順序；收合狀態仍要能理解功能名稱與當前狀態。
- 逐頁視覺驗證後才移除原本常駐的說明，不以單元測試通過取代可理解性檢查。

## 七、與 B8 的邊界

B8 只建立字級角色、遷移 token、調整長文節奏與文章波浪。B9 另行決定 icon 尺寸與哪些說明改為互動揭露。兩者可以共享語意 token，但不得在同一個一般清理 commit 中混做。

## 八、結案：漸進揭露不再推行（2026-08-29 裁決）

### 裁決

**停止「系統性把既有說明文字改成可展開」。不再有第三輪。**

**保留**的部分（這些沒有被否決，而且正在使用中）：

- **§3 的分類規則**——「常駐／可展開／不可隱藏」四類是這次得出結論的工具，也已經寫進 `DESIGN.md` 第五節與 `MorePage.test.ts` 的守門測試。**新增畫面時仍要用它判斷。**
- **§4 的互動契約**——5 個既有 disclosure 元件都照它實作（2026-08-29 裁決 2 統一）。**要做展開收合時仍以它為準**，權威版本在 `DESIGN.md`「展開收合（disclosure）」小節。
- **§2 的 icon 尺寸角色**——icon-first 已完成並上線（B9 第一輪）。

**收掉**的是 §1 的前提與 §5 的推行計畫：這個 App 有大量可以收的說明文字、應該逐頁去找出來。

### 證據

| 輪次 | 範圍 | 逐項分類的規模 | 實際可收 |
| --- | --- | ---: | ---: |
| 第一輪 | 「更多」頁 | 7 張卡 | **0** |
| 第二輪 | 三頁設定（`NotificationSettingsPage`、`ReportContextEventPage`、`EventCorrectionPage`） | 41 段 | **2**（都是一句話，加控制項不划算） |

第二輪 41 段的分布：錯誤與即時狀態 21 段（51%）、貼著控制項的決策條件 12 段、健康／安全邊界 3 段、不可逆操作後果 2 段、已經是 disclosure 1 段。

完整分類見 `docs/decisions/2026-08-29-b9-round2-disclosure-audit.md`。

### 為什麼是「前提不成立」而不是「還沒找到對的頁面」

三件事一起指向同一個結論：

1. **兩輪加起來 48 個判定單位，可收的只有 2 個，而且都是單句。** 這不是取樣不足，是分布如此。
2. **第二輪 51% 的段落是 `role="alert"` 或 `role="status"`**——本質上不能藏，不管換哪一頁都一樣。
3. **唯一一個成立的 disclosure 已經存在**：`NotificationSettingsPage` 的「如何開啟」＋瀏覽器設定步驟。它長、跟大多數人無關、只在權限被封鎖時才需要。**它示範了什麼樣的文字才適合收——而兩輪掃過的頁面裡沒有第二段長成那樣。**

第 3 點是關鍵：可收的文字不是「還沒找到」，而是這個產品**本來就很少產生那種文字**。它的說明幾乎都貼著某個控制項、講某個後果，或是某條健康邊界。

### 對之後的人

看到這份規格標題有「漸進揭露」四個字時，**不要把它當成待辦**。要新增展開收合時，判斷標準是單一項目自己的性質（照 §3 分類），不是「這頁段落很多所以應該收一些」。

**用段落數挑目標是這次真正犯的錯**——而且是 §5 自己明文禁止的事（「不只靠字數決定是否收合」）。第二輪的範圍建議就是照 `<p>` 數量排出來的，那個排序在寫下的當下就已經違反了本規格。
