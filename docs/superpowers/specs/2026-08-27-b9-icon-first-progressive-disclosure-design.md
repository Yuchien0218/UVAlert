# B9 Icon-first 與說明文字漸進揭露設計規格

**日期**：2026-08-27（Asia/Taipei）

**狀態**：方向已由產品端確認；待另行盤點與實作計畫

**範圍**：以 icon 建立第一視覺錨點、降低常駐說明文字量、定義可展開說明的互動與無障礙契約；不納入 B8 字級實作

## 一、問題與設計方向

目前部分畫面讓功能名稱、狀態、原理與補充說明同時常駐，每個區塊視覺重量接近，造成畫面壅擠。部分 icon 又偏小，只能成為文字附件，沒有形成清楚的掃讀入口。

採用已確認的方案 B：**一行必要標題＋按需展開說明**。icon 是第一視覺錨點，文字仍負責名稱與決策資訊；不採完全只剩 icon 的方案。

## 二、icon 尺寸角色

| 角色                  | 圖形尺寸 | 說明                                              |
| --------------------- | -------: | ------------------------------------------------- |
| `--icon-size-inline`  |     18px | 文字旁的輔助 icon，不主導區塊                     |
| `--icon-size-action`  |     24px | 導覽、按鈕、設定列的主要 icon                     |
| `--icon-size-feature` |     32px | 卡片或功能入口的主要視覺                          |
| `--tap-target`        |     44px | 最小操作範圍；不代表 icon 圖形本身必須放大到 44px |

大型狀態或品牌插圖不直接套入這三種 UI icon 尺寸，需另有元件規格。icon 放大不能破壞既有 Lucide 線寬、對齊或自訂圖示政策。

## 三、資訊分層

### 必須常駐

- 功能或設定名稱。
- 目前狀態、已選值、數量或會直接影響操作判斷的資訊。
- 錯誤、驗證訊息與必填條件。
- 不可逆操作的後果與健康／安全相關限制。
- 使用者採取動作前必須知道的條件。

### 可以按需展開

- 功能原理與「為什麼需要」的背景。
- 較長的使用範例或進一步解釋。
- 不影響當下決策的補充內容。
- 已被標題與狀態充分表達的重複說明。

不能以「縮短畫面」為理由，把健康內容的來源、審閱狀態、警告後果或表單錯誤藏起來。

## 四、互動契約

- 優先使用明確的資訊按鈕或可展開整列；同一種元件只能採一種一致模式。
- 控制項使用真實 `button`，設定 `aria-expanded` 與 `aria-controls`，可用 Enter／Space 操作。
- 展開後說明緊鄰其所屬項目，不使用離開上下文的全域 modal。
- 收合不清除使用者輸入、選擇或目前狀態。
- 重要內容不能只放在 hover tooltip；觸控裝置、鍵盤與螢幕閱讀器必須取得同等資訊。
- icon-only 操作必須有可存取名稱；不常見或具風險的操作仍需可見文字。

## 五、導入方式

B9 必須先逐頁列出候選說明文字，依「常駐／可展開／不可隱藏」分類，再改元件。不進行全站批次刪文，也不只靠字數決定是否收合。

第一輪優先考慮資訊密度較高、重複說明較多的設定與摘要畫面；核心提醒流程、錯誤狀態及健康內容先維持完整可見。每次導入需比較展開前後的理解程度、操作步數與版面高度。

## 六、驗證契約

- 針對收合／展開、鍵盤操作、焦點、`aria-expanded` 與狀態保存撰寫互動測試。
- 在 390px 行動版確認 icon、標題、狀態與控制不互相擠壓，且點擊範圍至少 44px。
- 在桌面版確認 icon 放大後沒有形成過多競爭焦點。
- 以 200% zoom 與螢幕閱讀器語意檢查內容順序；收合狀態仍要能理解功能名稱與當前狀態。
- 逐頁視覺驗證後才移除原本常駐的說明，不以單元測試通過取代可理解性檢查。

## 七、與 B8 的邊界

B8 只建立字級角色、遷移 token、調整長文節奏與文章波浪。B9 另行決定 icon 尺寸與哪些說明改為互動揭露。兩者可以共享語意 token，但不得在同一個一般清理 commit 中混做。
